# Plan: SPEC conformance audit, library rows

## Objective

Check every normative row of the dm-crypt activation, kernel-keyring and
loop-device documents against the code. Each requirement gets the code that
meets it and a unit test that fails if it breaks. A gap gets a test, or a fix
with a test. A fix that needs a design or API change is reported, not made.

## Slices, in order

1. dm-crypt activation, rollback and teardown: rollback and teardown tests,
   `internal/dm` retry budget and backoff, shared `ErrPermissionDenied`.
2. Kernel keyring: a repeatable preflight test.
3. Loop devices: find-by-identity tests, shared `ErrPermissionDenied`.
4. Final slice, dm-crypt retries and holder hints, keyring release message:
   - `TestDeactivateBusyMessageNamesTheHolderHints`: the `ErrBusy` detail
     names the attempts, the budget, `lsof`, `mount`, `dmsetup info -c` and
     `dmsetup remove --deferred`.
   - `TestRollbackStillLiveMessagesNameTheTargetAndRemedy`: both fail-closed
     rollback messages name the target and what to run.
   - `TestReleaseFailureMessageNamesTheEntryAndTheKeyctlCommands`: the
     `ErrKeyringKeyNotReleased` detail gives the `keyctl` commands.
   - `TestReleaseTreatsARevokedButResolvableEntryAsNotReleased`: the
     verification search accepts only `ENOKEY`/`ENOENT`.
   - `docs/kernel-keyring/engineering.md`: the verified-release row says
     which answers count as gone, at which step.
   - `docs/dm-crypt-activation/cli.md` and `docs/kernel-keyring/cli.md`
     checked against the CLI code. Neither needed a fix.

## Out of scope

- CLI end-to-end tests. Another row branch covers them.
- Design or API changes. They go in the report.
- `docs/SPEC.md`, `ROADMAP.md` and `.github/`.
